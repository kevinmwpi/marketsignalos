# Fix Lessons Learned

This log captures what we learn as we close the incomplete MVP gaps one at a time on branch `codex/address-incomplete-tasks`.

## Target Gaps

- Wire trade ingestion into the runner so the API's trade-backed endpoints have real source data.
- Define and implement the account enrichment producer used by the leaderboard API.
- Harden storage and data access beyond repo-local JSONL/JSON files.
- Improve observability and operational health beyond a basic `ok` health response.
- Expand deployment/runtime support for the web app and background ingestion.
- Grow the frontend from a single leaderboard page into a fuller product surface.

## Lessons

### 2026-07-07 - Settlement detection required a Gamma flag state that never occurs

- Issue: commit `67d0616` (2026-06-02) tightened `_market_winning_outcome` to require `closed=True` AND `active=False` before counting a market as resolved, and `signal_ledger._resolved_outcomes` mirrored the same rule. Gamma never flips `active` to `False` on resolution — an entire 13,043-market snapshot contained zero `active=False` rows, and all 500 closed markets in it were still `active=True` with settled 0/1 outcome prices. Every enrichment pass since 2026-06-02 therefore computed `resolved_bets=0` (no skill scores, empty skilled-bets feed) and the paper-trade ledger never settled a single signal.
- Fix: settlement now requires `closed=True` plus a unique >=0.99 winner, ignoring the `active` flag entirely (`skill_computation._market_winning_outcome`, `signal_ledger._resolved_outcomes`). The original intent of the strict rule — live markets trading at 99c must not count as resolved — is preserved by the `closed` requirement.
- Verification: recomputing enrichment on identical local data went from `resolved_bets=0` to `resolved_bets=550` (the snapshot's full closed-market population); all 305 Python tests pass; the test fixtures that previously encoded the wrong assumption (`active=not closed`) now pin the realistic Gamma state (`active=True` on resolved markets) so the suite regression-tests this exact failure.
- Lesson learned: the tests passed the whole time because the fixtures were built to satisfy the predicate rather than to mirror the upstream API. When a gate keys on an external system's flag combination, validate that the combination actually occurs in production data — one Counter() over the real JSONL would have caught this on day one.
- Follow-up: production (Railway) has been enriching with zero resolved bets since 2026-06-02 and its ledger rows never settle; deploying this fix and re-running enrichment there restores the feed, and the first post-deploy ledger refresh will settle the backlog.

### 2026-07-10 - Unbounded httpx cookie jar turned big ingests into O(n²) grinds

- Issue: `PolymarketClient` reuses one `httpx.Client` for every request, and Cloudflare sets cookies (`__cf_bm` variants) on responses. httpx accumulates every variant in the client's cookie jar and walks the entire jar while *building* each request (`http.cookiejar.deepvalues`). After tens of thousands of requests — whale-wallet activity paging, the 200k-condition market backfill — each new request cost minutes-to-hours of pure CPU inside cookie merging. Deep pipeline runs appeared to "freeze" mid-run with no error, no log output, and (misleadingly) a healthy-looking process.
- Fix: clear the client cookie jar after every response in `_get_json` and `_post_graphql` — these public APIs are cookie-free, so the jar must simply never grow. Also added transport-error retries (2026-07-08) so a single `ReadTimeout` no longer aborts an entire pipeline run.
- Verification: `py-spy dump` on a "frozen" run showed the main thread `active+gil` inside `cookiejar.deepvalues` during `build_request` — not blocked on any socket; a regression test asserts the jar stays empty after responses that set cookies.
- Lesson learned: diagnose stalls with a stack dump before assuming deadlock, OOM, or network hangs — three plausible theories (machine sleep, thread deadlock, dead sockets) each fit the symptoms and each was wrong. Also: on Windows venvs the console-script exe spawns a launcher python which spawns the real worker — measure the grandchild with the multi-GB working set, not the first python child, or the readings describe the wrong process.
- Follow-up: production Railway deep runs (`INGEST_DEEP_EVERY_N_RUNS`) issue the same request volumes in-process and would hit the same grind; ship this fix before enabling scheduled deep sweeps. The ~190k conditions Gamma returns no market for are re-requested every backfill — a negative-cache file would cut reference refresh by an order of magnitude.

### 2026-07-13 - Whale hydration accumulated whole activity histories in RAM

- Issue: `_hydrate_single_wallet` accumulated every fetched activity event into one in-memory `activity` list (incremental window + full-history backfill + subgraph backfill) and wrote it to the store only once at the end; `_paginate_activity_window` likewise collected an entire window into a `collected` dict before returning. Under the deep pipeline (`exhaust_activity=True`, page cap `POLYMARKET_ACTIVITY_EXHAUST_PAGES=2000` → up to 1,000,000 events per window) with 4 concurrent wallet workers, four whale histories plus the ~5 GB resident dedupe index pushed a deep run to 18 GB private on a 15.7 GB machine. It thrashed on the pagefile: one run sat 13.5 hours making zero disk progress at ~20% CPU (swap-bound), the API event loop starved so `/health` timed out, and the same class of load previously tripped a TDR BSOD. The streaming enrichment refactor had fixed the read side of the 30 GB activity file; this was the same unbounded-accumulation flaw on the hydration/write side.
- Fix: stream activity to disk page-by-page. `_paginate_activity_window` gained an optional `on_page` sink; when present it hands each page (main descending page + same-second boundary re-fetch) straight to the sink and returns an empty `events` list, so peak memory is one page instead of a whole history. `_hydrate_single_wallet` passes a sink that writes each page through the dedupe store immediately (under the shared write lock) and tracks the running max timestamp for the checkpoint; `_extend_activity_via_subgraph` threads the same sink. The dedupe index keeps per-page writes idempotent, so overlapping boundary re-fetches never double-write.
- Verification: a new equivalence test (`test_paginate_activity_window_streaming_matches_accumulate`) asserts the sink receives exactly the deduped event set the accumulate path returns — including a same-second boundary overlap — while `result.events` stays empty; the existing `run_wallets` checkpoint/economics tests exercise the sink end-to-end. Full ingestor suite 204 passing, ruff + mypy clean. A crash mid-wallet now leaves already-fetched pages durably on disk (idempotent on re-run) instead of losing the whole wallet.
- Lesson learned: fixing a memory blow-up in one pass (enrichment) does not fix its twin on the other side of the same giant dataset (hydration) — audit every path that materializes the 30 GB activity data, not just the one that crashed. The tell was process-level, not in the logs: 18 GB private on a 16 GB box with 0.66 GB free and a 13.5-hour-stale output file said "thrashing" long before any error did. `py-spy dump` on the worker grandchild confirmed the threads were in socket reads / JSON decode, not deadlocked.
- Follow-up: the dedupe index is ~2.7 GB on disk / ~5 GB resident and grows O(total rows); since a `(tx, condition, outcome, type)` key belongs to exactly one wallet, per-wallet dedupe would let it drop the global set entirely. Until then, run the first validating deep pass with `POLYMARKET_WALLET_CONCURRENCY=2` for extra headroom. Separately, `/signals/skilled-bets` streams the whole activity file per request (~400 s) for conviction scoring — it needs precomputation/caching before the dashboard is usable.

### 2026-07-14 - Undamped Newton diverged, saturating every wallet's skill to 1.0

- Issue: `fit_wallet_posterior` used a raw (undamped) Newton step `edge += -gradient/hessian`. On a near-flat objective — a near-separable wallet under a diffuse prior — that step overshoots wildly. A handful of wallets got pass-1 MLEs of 10^3–10^5, which poisoned the empirical-Bayes population prior (`mu=67.6, sigma2=1.07e7`). That diffuse, off-centre prior then removed all regularisation from every wallet's pass-2 fit, so Newton oscillated to ~10^10 and `skill_likelihood = P(edge>0)` saturated to 1.0 for **100% of wallets** (500/500 on the leaderboard). The skill signal — the core evidence of "who is skilled" — carried zero information, so the feed was effectively selecting wallets by volume.
- Fix: damped Newton with a backtracking line search on the concave log-posterior (accept a step only if the objective increases), plus a hard clamp of the edge to a physical domain (|edge| ≤ 20 log-odds). Also hardened `fit_population_prior`: per-wallet MLEs are clamped to the domain before taking moments and the fitted variance is capped (`_MAX_SIGMA2_POP`), so one degenerate fit can no longer blow up the prior.
- Verification: reproduced end-to-end on the real 906k-bet dataset — the population prior went from `(67.6, 1.07e7)` to `(0.057, 0.01)`, per-wallet edges from `4.5e10` to `~0.2`, and `skill_likelihood ≥ 0.999` from 100% of wallets to 1%. Only 3% now clear `skill≥0.8 AND edge_lower_bound>0`, which agrees with the independent CLV evidence (~20% of the CLV-sampled subset). Five regression tests pin the fix (the diffuse-prior case diverges to ~1e10 on the old code); full ingestor suite (209) + ruff + mypy green.
- Lesson learned: a fitted hyperparameter fed back into the same fitter is a feedback loop — one diverging sub-fit can silently destroy the whole population. Guard iterative optimisers with damping/line-search (never trust a raw Newton step on data that can be separable) and clamp any method-of-moments hyperprior to a sane domain. The tell was a nonsensical hyperparameter (`mu=67` log-odds is a ~10^29 odds ratio) logged every run — worth an alert.
- Follow-up: the fixed scores only reach the live feed after enrichment re-runs, which currently OOMs on the 1M-market catalog (task #5) — so this unblocks trustworthy scoring but #5 gates its delivery, and the tailable set will shrink/change once it lands. The strong shrinkage (sigma2 at the floor) says most apparent edge is noise; revisit whether the CLV-based gate (P1) should be the primary signal.

### 2026-03-19 - Trade ingestion was implemented but not orchestrated

- Issue: the trade pipeline, store, and worker already existed, but the runner only executed fills and resolutions.
- Fix: wired `KalshiTradeIngestionPipeline`, `JsonlTradeStore`, and `KalshiIngestionWorker` into the runner so each configured ticker now writes `kalshi_trades.jsonl` before downstream analytics consume it.
- Verification: added a runner-level test that exercises trade, fill, and resolution writes together and confirms checkpoint state for all three flows.
- Lesson learned: the biggest MVP gaps here are not always missing algorithms; sometimes the core parts exist but are never connected into the actual runtime path.
- Follow-up: the trade path now exists end-to-end, but the storage layer is still file-backed and append-only, so durability and operational robustness remain separate tasks.
